# Архитектура RoboLab

RoboLab имеет собственное дерево и историю Git. Учебные алгоритмы, полевые журналы и конфигурация Yahboom хранятся отдельно. Локальный оператор задаёт путь к установленному Yahboom, а агент публикует только встроенные профили из реестра. Приложение на клиенте никогда не передаёт агенту путь или команду оболочки.

## Этап 1

- `agent/` содержит FastAPI, реестр с одним поставляемым примером и управление дочерним процессом. Команда собирается из `sys.executable` и фиксированного файла, отдельными аргументами. Исполняемый пример не читает GPIO и камеру.
- `client/` содержит Flet и асинхронный транспорт. Пользователь вводит адрес и токен, выбирает скрипт, запускает или останавливает его, видит текущее состояние и журналы.
- `common/` содержит модели Pydantic для API. Фаза, PID, UTC-время, прошедшее время и код завершения передаются независимо от текста журнала.
- `examples/` содержит оригинальный Mock Robot. `tests/` проверяет API, процесс и поток на ПК.

На старте агент слушает loopback. Аутентификация HTTP и WebSocket использует заголовок `Authorization: Bearer …`. Токен читается из окружения агента и вводится в Flet. Для сети с недоверенными участниками нужен TLS или защищённый туннель. HTTP передаёт токен открытым текстом. Захват и трансляция камеры в первом этапе отсутствуют.

## Контракт

| Канал | Назначение |
| --- | --- |
| `GET /health` | Проверка связи, версии контракта и типа агента. |
| `GET /scripts` | Идентификатор, название, описание и манифест параметров скрипта. |
| `POST /runs` | Запуск по идентификатору из реестра с необязательным словарём `parameters`. |
| `POST /runs/{run_id}/heartbeat` | Подтверждение связи для текущего аппаратного запуска по его приватному идентификатору. |
| `POST /runs/{run_id}/stop` | Остановка конкретного запуска. |
| `POST /safety/stop`, `POST /safety/reset` | Аварийная блокировка и проверяемое снятие блокировки для Yahboom. |
| `WS /events` | Состояние последнего запуска, сообщения stdout/stderr и периодические обновления. |
| `POST /camera`, `DELETE /camera/{id}` | Явное начало и завершение просмотра. |
| `GET /camera/{id}/frame?after=N` | Последний JPEG после кадра N с метаданными или HTTP 204, пока нового кадра нет. |
| `GET /telemetry` | Системные показатели агента и последние числовые метрики сценария. |
| `GET /history`, `GET /history/{id}` | Список и подробности сохранённых запусков. |
| `GET /history/{id}/export?format=json\|csv` | Скачивание результатов запуска в выбранном формате. |

Единственный агент с одним worker управляет одним процессом за раз. Запуски сериализуются, конфликт получает HTTP 409. Остановка посылает сигнал и даёт процессу время штатно завершиться, после таймаута процесс принудительно завершается. Агент дочитывает журналы и возвращает итоговый статус и код. При отключении UI симулятор продолжает работу до остановки, штатного завершения или выключения агента. Его длительность ограничена собственными параметрами.

Агент держит в памяти только последний запуск и до 300 его строк. Каждая строка имеет номер в рамках запуска. После обрыва клиент повторно проверяет связь и открывает поток с последним подтверждённым номером. При переполнении буфера интерфейс отмечает пропуск. Если за время обрыва стартовал новый запуск, клиент принимает его состояние и новый журнал. Команды запуска и остановки автоматически не повторяются. Клиент получает актуальное состояние по восстановленному потоку.

## Этап 2

Манифест `examples/mock_robot.json` задаёт параметры GUI и правила сервера. Параметр имеет ключ, флаг argparse, название, описание, группу, тип и значение по умолчанию. Для чисел можно задать диапазон, для перечислений — список значений. Поле `requires` задаёт условия на поля, перечисленные раньше. Клиент строит форму из манифеста. Агент повторно проверяет значения, подставляет допустимые значения по умолчанию и передаёт каждый элемент argv непосредственно в процесс.

В реестре задан путь к CLI Mock Robot. Из каталога скриптов читается JSON, поэтому просмотр параметров не импортирует и не запускает Python-файл. Mock Robot разбирает те же параметры через argparse и может выполняться самостоятельно. Последние настройки и именованные пресеты хранятся в Flet SharedPreferences по адресу агента и идентификатору скрипта. Токен вводится заново при подключении. Параметры передаются при создании запуска.

## Этап 3

Адаптер Linux включает локально зарегистрированный дальномер Yahboom и опциональный профиль ультразвукового объезда. Агент добавляет фиксированный режим, путь к конфигурации и каталог журнала. Просмотр параметров читает описание из реестра. Подключение и запуск обходятся без просмотра камеры.

Эксклюзивный `flock` удерживается агентом, процессом сценария и процессом проверки GPIO. Прямые запуски под той же блокировкой выполняются последовательно. Аппаратный процесс запускается в отдельной группе. Агент прекращает группу при аварийной команде или истечении срока подтверждения связи. Независимый процесс на интерпретаторе Yahboom переводит BCM16 и BCM13 в LOW и считывает их состояние. Он выполняется перед стартом и перед отпусканием блокировки. Неудачная проверка блокирует новые аппаратные запуски.

Подтверждение связи начинается с ответа на аппаратный старт и истекает через 4 секунды после последнего подтверждения. Право подтверждать связь выдаётся только инициатору запуска и отсутствует в общем потоке статуса. Возврат связи не запускает процесс повторно. Снятие блокировки проверяет ENA и ENB и переводит агент в состояние готовности без запуска программы.

Физические испытания необходимы для подтверждения выключения приводов, остановки с нагрузкой и поведения на конкретной версии Pi и драйвера. Настройка и порядок проверки описаны в [инструкции для Yahboom](YAHBOOM.md).

## Этап 4

Клиент явно запускает и завершает просмотр. Агент запускает отдельный процесс OpenCV. Обработчик читает кадры и оставляет в памяти последний JPEG с номером и временем поступления. Клиент запрашивает кадры отдельно от WebSocket журналов. При закрытии просмотра агент завершает процесс. Без запросов кадров сеанс истекает через пять секунд. Закрытие блокирующего драйвера ограничено остановкой процесса.

На Yahboom камера использует общий замок с аппаратными сценариями. Аварийная остановка сначала завершает просмотр, если он запущен, затем выполняет проверку ENA/ENB. Канал просмотра управляет только своим процессом. Подключение кадров, уже полученных внешним алгоритмом, потребует интерфейса передачи от этого алгоритма. [Инструкция по камере](CAMERA.md)

## Этап 5

Агент сохраняет параметры и итог запуска в SQLite. У базы один поток записи. Чтение системных показателей Linux вынесено из цикла управления. Метрики алгоритма принимаются из JSON в stdout. Клиент отображает последние значения, график и сравнение нескольких запусков. [Формат метрик и хранение](EXPERIMENTS.md)

## Дальнейшая интеграция

Подготовить сборки клиента, CI и проверки на целевых устройствах.

Клиент и агент имеют независимые наборы зависимостей. Целевой минимум RoboLab — Python 3.11, чтобы сохранять возможность тестирования на Raspberry Pi OS Bookworm. Для интеграции внешних скриптов на Pi пригодятся локальные манифесты. Для автоматического получения параметров можно добавить статический разбор argparse. Реализация рассчитана на отдельное современное окружение агента, даже если внешний CLI требует более старого Python. Flet умеет упаковывать приложения для Linux, Windows и Android. Сборки и проверка пакетов на устройствах относятся к этапу релиза.

- [Требования Flet](https://flet.dev/docs/getting-started/installation/)
- [Матрица сборок Flet](https://flet.dev/docs/publish/)
- [WebSocket в FastAPI](https://fastapi.tiangolo.com/advanced/websockets/)
